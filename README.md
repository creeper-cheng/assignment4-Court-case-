# 作业 4 · 判案 API

用 3,520 份民事一审判决书做一个判案 API。输入一份判决书「本院认为」**之前**的部分（案情），
输出案由、适用法条、判决方向、判决主文。

## 接口

```
GET  /health                  → 200 {"ok": true}     不需要 key
POST /judge                   → {cause, laws, direction, verdict}
      Authorization: Bearer <key>
      {"case_text": "案情……"}
```

- 不带 key 或 key 不对 → 401
- 全部四项必填；**非流式**，单件 120 秒内返回（实测均值约 1.5 秒）

## 怎么做的

```
离线（python build_kb.py，约 17 秒）
  judgments.jsonl
    → 切分：案情 | 本院认为 | 判决主文 | 落款（丢弃落款后的「附：法律条文」）
    → 打标：案由 / 法条 / 判决方向 / 判决主文
    → _derived/kb.jsonl（3,520 条带标签的先例）+ BM25 倒排

在线（POST /judge，实测均值 1.5 秒）
  case_text
    → ① 抽案由（后缀闭包词表，98.8% 命中、0 噪声）
    → ② 在该案由桶内 BM25 检索 top-4 相似先例
    → ③ 把先例的「案情摘要 → 法条/方向/主文」作为少样本交给 DeepSeek
    → ④ 校验 + 兜底，只返回四个必填字段
```

**为什么不用向量检索**：案由过滤已经把范围从 3,520 缩到约 400，
桶内找相似案件靠关键词就够，且零嵌入成本（本地 CPU 上嵌入 3,520 份要 2.25 小时）。

**留出法验收**（`python tests/e2e.py`）：从 3,520 里挑 10 件、用环境变量把它们从检索里
排除，模拟"老师给的新案件不在语料里"。实测：

| 指标 | 结果 |
|---|---|
| 案由命中 | **10/10 = 100%** |
| 判决方向命中 | **8/10 = 80%** |
| 法条命中（至少一条） | **8/10 = 80%** |
| 耗时 | 均值 1.5s，最慢 2.0s |

## 跑起来

```bat
python build_kb.py      先建库（需要 judgments.jsonl）
run_judge.bat           起服务，监听 127.0.0.1:8000
```

`judge.env`（已 gitignore）需要：

```
JUDGE_KEY=你自己设的 key
LLM_BASE_URL=https://api.deepseek.com
LLM_API_KEY=sk-...
LLM_MODEL=deepseek-chat
```

## 开公网（Cloudflare Quick Tunnel）

```bat
winget install --id Cloudflare.cloudflared
```
装完**重开终端**，然后：

```
终端 A：run_judge.bat
终端 B：cloudflared tunnel --url http://127.0.0.1:8000
```
复制打印出的 `https://xxxx.trycloudflare.com`。连不上 Cloudflare 时加 `--protocol http2`。

## 几个实测踩出来的坑（都写在代码注释里了）

1. **必须先截落款再抽法条**。25.2% 的判决书在落款之后附了「附：法律条文《…》第…条」，
   不截的话每份都"引"七八条，全是附录里的。

2. **推理锚点不能只用 `find("本院认为")`**。1.9% 的文书首选措辞是「本院经审查认为」
   「法院认为」，而它们后面又会出现「本院认为」；只找后者会把前一段论证错划进案情段。
   要取 `本院认为|本院经(审理|审查)认为|法院认为` 里位置最靠前的。

3. **判决主文要同时按 `一、二、…` 和 `。；` 切项**。29% 的主文完全不用编号，
   不切句会把「给付…。驳回…」整体当成驳回而误判方向。

4. **`PROC_RE` 里绝不能加 `本判决生效后`**。标准给付句式就是「被告X于本判决生效后
   十日内给付原告Y…」，加了会在第一项就命中、把后面全切掉（连"驳回其他诉讼请求"一起），
   判决方向全部误判成"支持"（实测支持率从 44.8% 飙到 56.1%）。

5. **案由用「后缀闭包」抽取，不用正则硬切**。正则 `([一-鿿]{2,20}纠纷)一案` 看着命中 95.5%，
   但其中 31.8% 带出人名/公司名（`汕富物业有限公司诉被告隋学礼物业服务合同纠纷`）。
   改用数据驱动的后缀闭包后 0 噪声、98.8% 命中。

   闭包判据有两个坑：必须用**严格大于**（候选是窗口的所有后缀，完整案由和它去掉首字的
   形式 df 天然相等，用 `>=` 会把所有具体案由判成噪声、只剩泛称）；又必须带**容差**
   （`融借款合同纠纷` 比 `金融借款合同纠纷` 只多 1 份，严格 `>` 会把后者砍掉，
   约 400 份案子归到泛称「合同纠纷」）。

6. **判决主文里的当事人名称要明确要求"只能从案情原文取"**。主文一律「角色+名称」，
   角色可预测、名称不可预测；prompt 里不写死这条，模型会编名字。

7. **判"部分支持"要克制**。先例里 48.7% 是部分支持，模型会照搬句式、给每个案子都加
   「驳回原告其他诉讼请求」。必须在 prompt 里写明：只有本案原告确有部分请求站不住脚时才
   判部分支持，全部获支持时不要添加驳回项（实测方向命中率 70% → 80%）。

## 目录

```
kb.py            切分与标签抽取（纯函数，可离线自测）
build_kb.py      建库：kb.jsonl + BM25 倒排
serve.py         判案 API（标准库 HTTP）
llm.py           DeepSeek 非流式 JSON 调用
run_judge.bat    启动脚本
tests/selftest.py   离线自测：切分/案由/法条/方向
tests/e2e.py        留出法端到端验收
_derived/        建库产物（gitignore，可用 build_kb.py 重新生成）
```

判决书来自中国裁判文书网公开文书，仅用于课程作业。
